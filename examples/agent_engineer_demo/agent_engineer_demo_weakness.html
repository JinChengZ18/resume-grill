简历弱点分析

日期：2026-07-10｜对抗性技术面试 · Agent 开发工程师（示例）
⌂ 总入口✎ 简历优化◎ JD匹配

候选人A · Agent 开发工程师（2年）

主线清晰：一段与AI Infra高度对口的LLM网关生产经历，加上两段在读期间的研究与实习。最大的风险不在技术方向，而在三处会被重点追问的表述：标题里「2年」的经验口径、项目二通篇「参与」导致本人职责不清、项目三的评估机制没有评测口径。先改这三处，其余是表达层面的问题。

高 2中 3低 1

优先处理

  1. 标题去掉合并计算的「2年」，每段经历写明起止年月和性质（全职、兼职、实习）。
  2. 项目二逐条写出本人负责的模块或Agent Tool，用具体动作替换「参与」。
  3. 项目三给评估机制写明数据与结果；没有评测数据就改写成设计思路，不写成已验证的结论。
  4. 技能栏只保留项目里用过或能讲清楚的技术，Redis、ClickHouse找到出处再放进「熟练」。

保持不变的强项

  • LLM网关Exec-Layer的生产经历与岗位直接相关：多Provider统一转发、Token用量与推理成本统计、QPS监控是全简历最有说服力的部分，修改时保留这些具体名词。
  • 成果几乎没有堆砌没有基线的百分比，表述克制；改写时不要为了好看加入无法核验的数字。
  • Datadog迁移到Signoz、生产环境Memory Leak排查这类工程动作具体，可以在面试中展开验证。

逐条分析

W1

经验年限口径 高

简历原文
Agent 开发工程师(2年)
问题

全职工程经历只有Sahara AI一段（2025-09至2026-05，约8个月）；Capisoft（2024-12至2025-06）与绿盟实习（2024-07至2024-09）都在硕士就读期间（2022-09至2025-08）。「2年」是把在读经历合并计算的结果。

面试官会怎样理解

面试官对照时间线时会发现口径不一致，容易把后面的表述都按“可能有夸大”来读。按初级候选人评估本身不吃亏，口径不清才会影响可信度。

可能的追问

选问时机：看到标题里的年限，或发现经历与就读时间重叠时。

你写的是2年经验，能按时间顺序说说每一段是全职、兼职还是实习吗？

示范回答

可以。全职只有Sahara AI这一段，2025-09到2026-05，做LLM网关。之前两段都在硕士就读期间：绿盟是2024-07到2024-09的暑期实习；Capisoft是2024-12到2025-06，性质是【待补充：兼职、研究还是全职，以及每周投入时间】。简历上的「2年」是把这几段合在一起算的，严格按全职算是8个月左右。这几段做的都是后端和LLM应用，我更希望按实际做过的内容来评估。

怎么改

标题去掉年限，或写成「全职约8个月＋在读期间经历2段」；每段经历写明起止年月和性质（全职、兼职、实习）。

改写示例

Agent/AI Infra后端工程师｜Sahara AI全职（2025-09至2026-05）｜在读期间经历2段

W2

本人职责不清（项目二Sorin） 高

简历原文
参与开发……参与部署……参与 Cloud Run 运行维护
问题

整段几乎都是「参与」，看不出哪些Agent Tool、哪些代码由本人完成，也看不出本人在部署中负责什么。

面试官会怎样理解

面试官会把这段当作团队项目，默认个人贡献偏小，并逐项追问“你具体写了哪部分”。如果到面试时才说清，会显得简历和实际不一致。

可能的追问

选问时机：看到「参与」类表述时。

Sorin里你自己负责的是哪几个模块或Agent Tool？挑一个讲讲设计取舍。

示范回答

我负责的是【待补充：模块或Tool名称】，从设计、实现到测试都是我写的；部署方面我做的是【待补充：具体工作】，Cloud Run的整体方案不是我定的。挑一个讲的话，我会讲【待补充：最有把握的Tool】：它要解决的问题、为什么拆成独立的Skill、遇到的最大困难和我的处理办法。

选问时机：候选人把架构说成本人设计时。

「可模块化打包的Agent Skill架构」是你设计的，还是在已有方案上实现的？

示范回答

整体方案是【待补充：团队或负责人】定的，我按这个方案实现了【待补充：哪些Skill】，自己做的改进是【待补充：改进点】。这个架构的好处是每个Skill可以单独测试和替换；代价是Skill之间需要共享上下文时要额外设计接口。

怎么改

每条写成「动作＋对象＋本人范围」，例如「独立实现X、Y两个Agent Tool，负责接口设计与测试」；部署部分写清本人做了什么，没做过的不写。

改写示例

独立实现【待补充：Tool名称】等【待补充：数量】个Agent Tool，负责【待补充：本人负责的环节】；在Cloud Run部署中负责【待补充：具体工作】。

W3

评估机制没有口径（项目三） 中

简历原文
多维度 Selector 评估（结构相似度/语义相关性/噪声抗性）；基于队列的 HTML 分层解析算法
问题

三个评估维度只有名称，没有数据集、样本量、计算方法和结果；“算法”一词也没有说明与常规分层遍历的区别。

面试官会怎样理解

面试官会请你逐个给出指标的计算方法和实测结果。给不出时，这一段会被当成概念描述，连带影响对项目完成度的判断。

可能的追问

选问时机：候选人提到评估机制或说效果好时。

结构相似度、语义相关性、噪声抗性分别怎么计算？在多少页面上评过，结果如何？

示范回答

结构相似度是【待补充：计算方法】，语义相关性是【待补充：计算方法】，噪声抗性是【待补充：计算方法】。评测用了【待补充：站点与页面数量及来源】，结果是【待补充：结果】。如果当时没有做系统评测，我会直接说明：这三个维度是设计时的筛选标准，验证方式是【待补充：实际验证方式】。

选问时机：简历出现「算法」「机制」这类词时。

为什么要基于队列做分层解析？和直接递归遍历DOM相比有什么好处？

示范回答

用队列做的是按层的广度优先遍历，可以先处理靠近根部、结构信息集中的区块，再配合分块控制每次送给LLM的内容长度，避免深层嵌套一次放进太多内容；代价是同一内容可能被拆到不同批次，合并结果时要去重。我们具体的分层规则是【待补充：规则】。

怎么改

写出评测设置与结果，例如在多少站点、多少页面上验证，回放命中率多少；没有评测数据就改写成设计思路，不用暗示已验证的词。

改写示例

设计结构相似度、语义相关性与噪声抗性三项指标，筛选LLM生成的CSS Selector；在【待补充：站点与页面数量】上验证，回放命中率【待补充：结果】。

W4

技能栏与项目对不上 中

简历原文
个人技能：Redis、ClickHouse
问题

两项技术只出现在技能栏；三个项目里用到的数据库是PostgreSQL和InfluxDB。

面试官会怎样理解

面试官常从技能栏挑没有项目出处的词来问，例如Redis的持久化方式、ClickHouse的表引擎。答不上来会让人怀疑整个技能栏的可信度。

可能的追问

选问时机：简历的技能与项目对不上时。

你在哪里用过ClickHouse？用它解决了什么问题？

示范回答

我是在【待补充：项目、课程或自学场景】里用的ClickHouse，用来【待补充：存储或分析的数据】。项目里的监控指标最终放在InfluxDB，是因为【待补充：原因】。

怎么改

技能按熟练程度分组，只把项目里用过的技术放在「熟练」；Redis、ClickHouse在项目里找到出处就写进对应条目，找不到就移到「了解」。

改写示例

熟练：Python、FastAPI（异步）、PostgreSQL、InfluxDB、Kubernetes、Cloud Run、Signoz、Langfuse；了解：Redis、ClickHouse

W5

自研与开源的边界（Exec-Layer） 中

简历原文
多 Provider 统一转发；建立 QPS、Token Usage、Inference Cost 监控
问题

这些能力与开源LLM网关（如LiteLLM）的功能高度重合，简历没有说明是自研、基于开源二次开发，还是集成现有组件。

面试官会怎样理解

面试官一定会问哪部分是自己写的。主动说明基于开源改造并讲清改了什么是加分；说不清楚，容易被理解成把开源能力当成自研。

可能的追问

选问时机：候选人强调网关能力时。

Exec-Layer是从零写的，还是基于LiteLLM之类的开源网关？改了哪些地方？

示范回答

Exec-Layer是【待补充：自研，或基于某个开源项目】。我们在原有基础上改了【待补充：改动，例如计费口径、鉴权或流式计量】，原因是【待补充：原因】。我本人负责的是【待补充：本人负责部分】。

选问时机：继续追问计量细节时。

流式返回时Token用量怎么统计？上游没有返回usage怎么办？

示范回答

有的上游会在流的最后一个数据块里带usage，有就以它为准；没有的话，用与模型匹配的分词器按输入和累计输出估算，并把这类记录标成估算值，对账时与上游账单核对差异。我们当时的做法是【待补充：实际做法】。

怎么改

在条目里写明实现方式（自研，或基于哪个开源项目二次开发）和本人负责的部分。

改写示例

基于【待补充：自研或开源项目】实现LLM网关Exec-Layer：统一转发【待补充：数量】家模型服务商的请求，按请求统计Token用量与推理成本，建立QPS监控；本人负责【待补充：模块】。

W6

结果缺少规模与基线 低

简历原文
提升可观测性；支撑生产流量
问题

成果是定性描述，看不出规模（请求量、接入服务数）和改进前后的差别。

面试官会怎样理解

定性写法本身诚实，但面试官无法判断工作量和难度，往往会当场追问规模；写出可核验的规模信息会更有说服力。

可能的追问

选问时机：简历没有规模信息时。

网关大概承载多大的流量？迁移到Signoz后，排查问题的方式有什么变化？

示范回答

网关的峰值大约是【待补充：QPS或日请求量】，接入了【待补充：服务或租户数量】。迁移前用Datadog，换掉它的原因是【待补充：迁移原因】；迁移后指标、链路和日志在同一套系统里查看，【待补充：迁移后的具体变化】。

怎么改

只写能核验的规模和对比，例如请求量、接入服务数、迁移前后的成本或告警时延；拿不到数字就写清范围和对象，不编造百分比。

改写示例

完成Datadog到Signoz的可观测性迁移，覆盖【待补充：服务数量】个服务的指标、链路与日志；【待补充：迁移后可核验的变化】。
