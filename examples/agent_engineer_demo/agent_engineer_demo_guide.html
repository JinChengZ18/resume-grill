核心验伪题（含答案键；题号对应评分卡 ★）

Q1

LLM 网关：流式 Token 计量与成本核算项目一 Exec-Layer「建立 QPS、Token Usage、Inference Cost 监控」「多 Provider 统一转发」

提问阶梯（由浅入深，从简历项目起手）
L1 项目切入一个请求从进入 Exec-Layer 到把上游响应返回给客户端，整条链路经过哪些环节？其中哪几块是你亲自写的、哪几块是团队既有的？
L2 设计决策用户级限流你限的是 QPS（请求数）还是 Token 预算？这两者实现完全不同，你们实际限哪个、为什么，计数落在 Redis 还是 Postgres？
L3 情境讨论
流式（SSE）转发下你怎么把 Token Usage 算准并计费——OpenAI 流里默认不带 usage、非 OpenAI 兼容 provider 干脆不给 usage、客户端流到一半断连，这三种情况分别怎么处理？推理成本又怎么按请求发生当时的价格算、而不被后来的调价追溯改写？
期望的优质回答
  • 流式必须用 async generator/StreamingResponse 边收边转，不能缓冲全部再吐；客户端断连要主动 cancel 上游请求，否则连接与成本泄漏
  • OpenAI 流默认无 usage，需显式传 stream_options:{include_usage:true} 才在末帧给出；拿不到就按累积 chunk 文本用对应 tokenizer 估算并标注为估算值
  • 各家 tokenizer 不同，tiktoken 只对 OpenAI 系准，Anthropic/Gemini 编码空间不同；input 侧还有 chat 模板、tool schema、多模态的隐藏 token，自估与账单有系统性偏差，务实做法以 provider 回传 usage 为准
  • Token 预算限流难点在 output token 事前不可知，须先预扣（reserve）再按真实 usage 结算（reconcile）；QPS 限流才是简单的固定/滑动窗口计数
  • 计数放 Redis 做原子操作（INCR+过期/Lua 脚本/sorted set 滑窗），Postgres 只落最终账单；并发下 check-then-act 竞态用原子原语防超额透支
  • 定价表带生效时间戳/版本，按请求发生时间取当时单价并把单价快照进账单记录，含 cached prompt 折扣价、input/output 分开计价、模型别名映射到计价 SKU
  • 断连场景要明确且前后一致的计费口径（按已收到 token 计，或明确不计费）
追问

你们内部统计的 token 成本和月底 provider 的真实账单差多少？这个差异你怎么归因和收敛，最终以谁的数出账给用户？

及格线（必须听到）
  • 知道流式要边收边转、断连需 cancel 上游
  • 知道 OpenAI 需 stream_options.include_usage，或说得出无 usage 时的兜底估算办法
  • 承认自估与 provider 账单有偏差、最终以 provider usage/账单为准
  • 定价按请求当时单价快照、历史账单不被调价改写
  • 区分 QPS 限流与 token 预算限流的本质差异
需进一步了解

说「把流收完再统一返回」（等于没做流式）；张口「tiktoken 一律能算」不知各家 tokenizer 不同；定价「配置里写死、改的时候直接改」（历史账单会被追溯篡改）；把 QPS 限流和 token 预算混为一谈；说不清断连怎么计费。

Q2

可观测性：高基数指标与 OTel 采集链路项目一「建立 QPS/Token/Cost 监控体系」「Datadog→Signoz 迁移」，技能栏 ClickHouse

提问阶梯（由浅入深，从简历项目起手）
L1 项目切入迁到 Signoz 之后，应用侧的 metrics/traces/logs 是怎么送出去的？这套采集链路哪一部分是你亲手搭的？
L2 设计决策Signoz 内核是 OTel+ClickHouse，你的 Collector 以什么形态跑在 K8s 里（sidecar/DaemonSet/Deployment），为什么这么选，为什么不让应用直连后端？
L3 情境讨论
Token Usage 这个 metric 的 label 维度你放了什么？user_id、api_key 这种 per-user 维度你是当 metric label 打上去、还是放别处？如果打成 label 会发生什么？你怎么既要实时聚合大盘、又要可追溯到单请求的成本明细？
期望的优质回答
  • 明确区分低基数维度（model/provider/status_code/route）适合做 metric label，高基数维度（user_id/api_key/request_id）绝不进 metric label
  • per-user/api_key 用量走 trace/log 的 attribute，或单独的用量明细表（Postgres/ClickHouse 明细）来算账单
  • 能算出「各维度取值数的笛卡尔积＝时间序列数」，理解 cardinality 爆炸会打垮存储与查询
  • 采集走 OTel SDK→OTLP（gRPC 4317/HTTP 4318）→Collector，Collector 有 receiver/processor/exporter 三段 pipeline，含 batch、memory_limiter、k8sattributes/resource 补 pod/namespace 标签
  • 不让应用直连后端以获得解耦、重试、采样、背压；DaemonSet 收节点级日志、Gateway Deployment 做集中处理与批量导出
  • 提 exemplar 把 metric 关联到 trace；ClickHouse 对高基数比 Prometheus 友好但也非无上限
  • 迁移动因是 Datadog 按主机/摄入量/custom metric 与高基数罚单的费用，诚实说出自托管 ClickHouse 的运维负担（TTL/分区/备份/升级）与损失的 Datadog 成熟能力
追问

技能栏还写了 InfluxDB，为何监控里两个时序库并存？给一个真实 measurement 的 schema——tag 放什么、field 放什么，为什么 user_id 绝不能进 tag？

及格线（必须听到）
  • user_id/api_key 不进 metric label，明确知道 cardinality 爆炸后果
  • 成本明细走明细表或 trace/log attribute，与聚合大盘分工清楚
  • 知道 Signoz 背后是 OTel+ClickHouse、采集经 Collector
  • 迁移能说出真实成本取舍，而非「开源不花钱就更好」一边倒
需进一步了解

「都打上去方便查」；把 per-user 用量做成 Prometheus gauge；没听过 cardinality；把 Signoz 当装个 agent 的 SaaS、不知 ClickHouse 在其中的角色；ClickHouse 写在技能栏却讲不出它干什么。

Q3

异步阻塞隔离与 Cloud Run 长请求项目一「FastAPI 异步」「优化含 LLM 推理的长耗时请求链路」，项目二「参与 Cloud Run 部署运行维护」

提问阶梯（由浅入深，从简历项目起手）
L1 项目切入一个请求从 FastAPI 的 async 路由到返回上游响应，整条链路哪些环节是 async、哪些是同步阻塞？点名你实际用的 HTTP 客户端和数据库驱动。
L2 设计决策转发上游你用 httpx，client 是每个请求新建还是全局复用？连接池的 max_connections、keep-alive、超时你设了没、设成多少、为什么？
L3 情境讨论
如果在 async 路由里误用了同步阻塞库（requests/psycopg2/time.sleep），单实例并发 50 个请求会发生什么、为什么？Cloud Run 上跑长耗时 LLM 请求，request timeout 设多少、单实例 concurrency 设几、为什么——把「平台层 concurrency」和「进程内 async 并发」这两层讲清楚。
期望的优质回答
  • async 路由里跑同步阻塞会卡死整个事件循环，其余并发请求全被拖住；必须换异步驱动（httpx.AsyncClient/asyncpg），迫不得已用 run_in_executor 丢线程池
  • httpx client 全局单例在 lifespan/startup 建、shutdown 关，靠连接池复用；用 httpx.Limits 配连接池规模（max_connections/max_keepalive_connections），用 httpx.Timeout 分别设 connect/read/write/pool 超时
  • 流式响应下 read timeout 要放宽或改 stream，否则长响应被误判超时
  • Cloud Run 请求超时最长 60 分钟（默认 5 分钟）、container concurrency 默认 80；LLM 慢请求要调低 concurrency，因每请求占内存与上游连接，否则排队与 OOM
  • 平台层 concurrency 决定单实例同时接多少请求，进程内 async 并发是事件循环层，两层叠加；CPU 配额是否 always-allocated 影响后台任务与计算段
  • Agent workflow latency 分段定位：用 Langfuse 看每次 LLM call 时延、用 trace span 拆各 tool 调用，常见瓶颈是多个 tool 串行而非 LLM 本身，改 asyncio.gather 并发并用 Semaphore 限并发防打爆上游 rate limit
  • 并发编排失败隔离用 gather(return_exceptions=True)/TaskGroup，每个 tool 包 asyncio.wait_for 单独超时，失败降级返回部分结果
追问

你说某个 tool 慢——你怎么确认是它的网络/上游慢，而不是它在排队等事件循环、或等某个共享连接池的锁？trace 里你具体看哪两个时间戳之差？

及格线（必须听到）
  • 理解 async 路由里同步阻塞会卡死事件循环、拖垮整实例并发
  • httpx 全局复用＋连接池＋分层超时
  • 说得出 Cloud Run concurrency/timeout 量级，并知道对 LLM 慢请求要调低 concurrency 的理由
  • latency 会分段定位（Langfuse/trace span），而非一律甩锅 LLM
需进一步了解

「全用 async，FastAPI 本身就是异步」却说不出客户端库名；每请求新建 AsyncClient 而不自知；把冷启动当成所有慢的原因；分不清平台层 concurrency 与进程内 async 并发；latency 笼统归给「LLM 推理慢没办法」。

Q4

Agent Skill 模块化与金融数字防幻觉项目二 Sorin「可模块化打包的 Agent Skill 架构」「LLM 动态生成 Markdown 分析结果」

提问阶梯（由浅入深，从简历项目起手）
L1 项目切入Sorin 里你具体独立写了哪几个 Agent Tool、哪些代码是你的？先讲讲这个系统你负责的部分。
L2 设计决策一个 Skill 在你们系统里是什么形态的产物（pip 包／带清单的目录／DB 记录）？主 Agent 通过什么机制发现并加载它，是进程内 import、importlib 动态加载还是跨进程调用？
L3 情境讨论
金融场景最怕模型把价格、涨跌幅、市值这些数字编出来。你怎么保证 Markdown 输出里的数字确实来自 tool 拿到的真实数据、而不是模型顺口生成的？别说「prompt 里让它别编」——讲程序化机制。
期望的优质回答
  • 数字与叙述分离：tool 返回的结构化数值单独保存，展示的关键数字直接从数据层模板占位／后处理填充，而非让模型自由书写
  • 或对模型输出的数字做回校验：提取正文数字与 tool 数据比对，不一致则标注或重生成；数字可能被换算（百分比、单位）需做匹配
  • 坦承纯靠 prompt 约束与 temperature=0 不可靠，必须有输出侧的 grounding 校验这一层
  • Skill 形态具体：带 manifest（skill.yaml/entry_points）的目录，声明 name/version/入口/所需 tool 与权限；主 Agent 扫描 registry 用 importlib 或 entry_points 发现加载；能讲依赖隔离与版本冲突取舍
  • tool orchestration 用 function calling 提供 JSON schema，模型返回结构化 tool_call，先做 pydantic 参数校验再执行，结果回灌
  • 幻觉参数兜底：tool 内做业务校验（ticker 是否在已知集合、日期合法性），数据源返回结构化错误让模型改参而非整链挂掉，有重试上限防死循环
  • 输出正确性分两层评估：可客观校验部分（数字溯源通过率、tool 调用准确率、格式合法率）用测试集回归，主观分析质量用人工抽检/LLM-judge 并承认其局限
追问

给一个你真实发现过的错误案例——Agent 输出了看起来合理但实际错误的结论，你怎么发现、事后加了什么机制防再犯？如果一个都举不出来，你凭什么确定它一直是对的？

及格线（必须听到）
  • 有输出侧数字溯源／校验机制，不是纯 prompt 祈祷
  • Skill 能说清打包格式＋发现机制＋加载入口，区别于「只是分了几个文件」
  • tool 参数有 schema 校验，幻觉参数有兜底与恢复路径
  • 有某种客观评估，而非「跑通没报错就发」
需进一步了解

答案停在「prompt 里强调只能用给定数据」「用了 temperature=0」；只重复「模块化/可复用」却说不出打包格式与发现机制；假设模型参数总对、tool 无校验直接透传；把「不报错」当成「结论正确」。

Selector 评估三指标与回放命中验证项目三「多维度 Selector 评估（结构相似度/语义相关性/噪声抗性）」「基于队列的 HTML 分层解析」

提问阶梯（由浅入深，从简历项目起手）
L1 项目切入这个抓取系统的完整流程走一遍——从一个 URL 进来到产出可执行 scraper，中间经过哪些步骤？
L2 设计决策「基于队列的 HTML 分层解析」入队的是 DOM 节点还是 HTML 字符串片段？什么条件下决定这一层就地切成一个 chunk，超长子树是硬截断还是递归下潜，祖先上下文怎么不丢？
L3 情境讨论
三个评估指标分别给出精确到可计算的定义——结构相似度拿什么和什么比、用什么距离（树编辑距离/路径重合）；语义相关性向量从哪来、和谁算余弦；噪声抗性扰动什么、如何量化「抗住了」。每个指标的判定阈值是多少、这阈值怎么标定出来的？另外生成的 selector 你回放到真实 DOM 验证命中数没有、命中 0 或命中多怎么处理？
期望的优质回答
  • 结构相似度＝目标元素与参考锚点两条 DOM/xpath 路径的序列编辑距离（Levenshtein）或路径重合度，也可用最长公共祖先深度归一化；若对元素子树整体度量才用树编辑距离（tree edit distance）
  • 语义相关性＝元素周边文本（或 aria-label/标题）embedding 与查询意图 embedding 的余弦
  • 噪声抗性＝对页面扰动（增删无关节点、改 class 后缀、注入广告 div）后 selector 是否仍命中同一元素，用命中保持率量化
  • 阈值诚实说明是自己标注的一批页面上调出的经验值，或坦白只有一两个真落成打分公式、另一个是启发式，而非硬报一个漂亮数字
  • selector 必回放到真实渲染 DOM（Puppeteer page.$$／jsdom querySelectorAll）执行：命中 0 触发带反馈的重生成，命中多个用预期文本/属性/nth-of-type/结构路径二次过滤或让 LLM 裁决，并对命中元素做内容断言而非只看数量
  • 分层解析入队 DOM 节点，BFS 按层展开，切分终止条件是子树序列化 token 数≤阈值（留出 prompt＋输出余量约 6~8k），超阈值递归下潜，每个 chunk 带 root 到该节点的祖先标签＋关键属性 breadcrumb，先做属性裁剪（去 style/内联 script/base64）压体积
  • 幻觉双层防线：生成侧把子树真实出现的 tag/class/id 作受限词表放进 prompt 或只让模型输出路径决策由程序拼 selector；执行侧回放兜底，并能给测试集规模、命中率/最终成功率、静态与动态页分层数据
追问

简历写「复杂企业文档场景下的稳定性与鲁棒性」——企业文档具体指哪类页面（登录后系统／PDF 转 HTML／内网报表）、样本从哪来、该场景成功率多少？如果没有真实数据支撑，你愿意把这句改成什么更准确的表述？

及格线（必须听到）
  • 三指标至少给得出输入是什么、和谁比、用什么度量，阈值来源诚实（标注集调出/部分是启发式）
  • selector 一定回放真实 DOM 校验，命中 0/命中多有明确分支
  • 分层解析的入队单元、切分终止条件、祖先上下文保留自洽
  • 拿得出命中率/成功率数字，或诚实承认只是原型量级
需进一步了解

三指标只能重复中文名词或翻成英文，给不出度量与阈值出处；张口报「相似度 0.85 以上」却说不清怎么标定、在多少页面验证过；「LLM 生成的 selector 准确率很高基本不用验证」；分层解析被追问就改口成固定字符数滑窗；用「稳定性大幅提升」这类无基线形容词搪塞。

L3 情境讨论
readiness 和 liveness 探针分别探哪个端点、失败几次才算挂、initialDelay 给多少、为什么这么设？另外上游各家 provider 的 API Key 在 K8s 里怎么存、怎么注入进容器、怎么轮换？一把上游 Key 泄露了，你的回收流程是什么？
期望的优质回答
  • requests（调度依据/保证值）与 limits（上限，超内存会 OOMKill）区别清楚，数值有依据（内存 limit＝观察峰值＋余量）
  • readiness 探轻量 /healthz 且不依赖上游、liveness 探进程存活避免误杀，两者不指向同一个重接口
  • initialDelaySeconds 要盖住应用启动时间，failureThreshold 不能太敏感否则滚动更新抖动，能说清 periodSeconds
  • K8s Secret 默认只是 base64 非加密，需开 etcd 加密或用 GCP Secret Manager，配 Workload Identity 让 Pod 免密钥访问 GCP，通过 env 或挂载 volume 注入
  • 轮换靠 Secret Manager 更新版本＋滚动重启；泄露时先在上游控制台吊销旧 Key、更新新版本、滚动重启摘掉旧 Key
  • 区分自家发给用户的 API Key 与上游 Provider Key 是两套东西、存储策略不同
  • 转发层瓶颈多在 I/O 等上游、CPU 利用率低，纯按 CPU 扩 HPA 不灵，应按并发数/in-flight 请求等自定义指标扩，或诚实说固定副本手动调；回滚 K8s 用 kubectl rollout undo，Cloud Run 靠切流回上一个 revision
