要听的点（★为及格线）
L2 设计决策

用户级限流你限的是 QPS（请求数）还是 Token 预算？这两者实现完全不同，你们实际限哪个、为什么，计数落在 Redis 还是 Postgres？

情境题前两问答得扎实再问

流式（SSE）转发下你怎么把 Token Usage 算准并计费——OpenAI 流里默认不带 usage、非 OpenAI 兼容 provider 干脆不给 usage、客户端流到一半断连，这三种情况分别怎么处理？推理成本又怎么按请求发生当时的价格算、而不被后来的调价追溯改写？

追问上一问答得好再追问

你们内部统计的 token 成本和月底 provider 的真实账单差多少？这个差异你怎么归因和收敛，最终以谁的数出账给用户？

期望的优质回答（点开查看）
  • 流式必须用 async generator/StreamingResponse 边收边转，不能缓冲全部再吐；客户端断连要主动 cancel 上游请求，否则连接与成本泄漏
  • OpenAI 流默认无 usage，需显式传 stream_options:{include_usage:true} 才在末帧给出；拿不到就按累积 chunk 文本用对应 tokenizer 估算并标注为估算值
  • 各家 tokenizer 不同，tiktoken 只对 OpenAI 系准，Anthropic/Gemini 编码空间不同；input 侧还有 chat 模板、tool schema、多模态的隐藏 token，自估与账单有系统性偏差，务实做法以 provider 回传 usage 为准
  • Token 预算限流难点在 output token 事前不可知，须先预扣（reserve）再按真实 usage 结算（reconcile）；QPS 限流才是简单的固定/滑动窗口计数
  • 计数放 Redis 做原子操作（INCR+过期/Lua 脚本/sorted set 滑窗），Postgres 只落最终账单；并发下 check-then-act 竞态用原子原语防超额透支
  • 定价表带生效时间戳/版本，按请求发生时间取当时单价并把单价快照进账单记录，含 cached prompt 折扣价、input/output 分开计价、模型别名映射到计价 SKU
  • 断连场景要明确且前后一致的计费口径（按已收到 token 计，或明确不计费）

一个请求从 FastAPI 的 async 路由到返回上游响应，整条链路哪些环节是 async、哪些是同步阻塞？点名你实际用的 HTTP 客户端和数据库驱动。

情境题前两问答得扎实再问

追问上一问答得好再追问

你说某个 tool 慢——你怎么确认是它的网络/上游慢，而不是它在排队等事件循环、或等某个共享连接池的锁？trace 里你具体看哪两个时间戳之差？

期望的优质回答（点开查看）
  • async 路由里跑同步阻塞会卡死整个事件循环，其余并发请求全被拖住；必须换异步驱动（httpx.AsyncClient/asyncpg），迫不得已用 run_in_executor 丢线程池
  • httpx client 全局单例在 lifespan/startup 建、shutdown 关，靠连接池复用；用 httpx.Limits 配连接池规模（max_connections/max_keepalive_connections），用 httpx.Timeout 分别设 connect/read/write/pool 超时
  • 流式响应下 read timeout 要放宽或改 stream，否则长响应被误判超时
  • Cloud Run 请求超时最长 60 分钟（默认 5 分钟）、container concurrency 默认 80；LLM 慢请求要调低 concurrency，因每请求占内存与上游连接，否则排队与 OOM
  • 平台层 concurrency 决定单实例同时接多少请求，进程内 async 并发是事件循环层，两层叠加；CPU 配额是否 always-allocated 影响后台任务与计算段
  • Agent workflow latency 分段定位：用 Langfuse 看每次 LLM call 时延、用 trace span 拆各 tool 调用，常见瓶颈是多个 tool 串行而非 LLM 本身，改 asyncio.gather 并发并用 Semaphore 限并发防打爆上游 rate limit
  • 并发编排失败隔离用 gather(return_exceptions=True)/TaskGroup，每个 tool 包 asyncio.wait_for 单独超时，失败降级返回部分结果
